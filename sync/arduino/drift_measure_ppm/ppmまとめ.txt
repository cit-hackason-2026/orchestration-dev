ppm 補正まとめ
==============

集計フォルダの drift_measure 計測結果(各楽器 5回ぶん)から、各 Arduino
UNO R4 WiFi の固有クロックドリフトを ppm に換算し、補正版の drift_measure
として drift_measure_2.ino を新規作成した記録。


1. 集計CSVから算出した ppm 値
------------------------------
120BPM(2秒/小節)に対する平均ドリフトを外れ値除去後に平均し、ppm に換算:

  flute    (0x10) : +2838 µs/小節  →  +1419 ppm   (時計が速い)
  clarinet (0x11) : +1237 µs/小節  →   +618 ppm   (時計が速い)
  organ    (0x12) : -1167 µs/小節  →   -584 ppm   (時計が遅い)
  drum     (0x13) : +3743 µs/小節  →  +1872 ppm   (時計が速い、最大)

ppm への換算式:
  ppm = ドリフト(µs/小節) ÷ 公称小節長(µs) × 1,000,000
      = ドリフト ÷ 2,000,000 × 1,000,000
      = ドリフト ÷ 2

「+」は自分の micros() が実時間より速く進む個体、「-」は遅い個体。


2. 制作物: drift_measure_2.ino
-------------------------------
元の drift_measure.ino をベースに、上の ppm 値を補正として組み込んだ
測定専用版。スレーブに焼き込んだ ppm 補正が実機で本当に効いているかを
確認するために作った。

変更点(元との差分):
  - クロックドリフト補正定数(ppm)を追加
    MY_I2C_ADDRESS の値に応じて #if で自動選択するようにした。
      0x10 → +1419 / 0x11 → +618 / 0x12 → -584 / 0x13 → +1872
      未測定アドレスは 0 ppm(補正なし)。

  - calcBarUs() を calcBarUsCorrected() にリネームし、ppm 補正を追加
    公称小節長(60000000 × 4 × 10 / bpm_x10)に
    「公称小節長 / 1000 × ppm / 1000」を加算して返すようにした。
    AVR の int32 オーバーフローを避けるため /1000 してから掛けている。

  - loop() 内の drift 計算式の意味が変わった
    元: drift = interval - 公称小節長(無補正)  → そのボードの生ドリフト
    新: drift = interval - 補正後の公称小節長  → 補正後の残差ジッタ

  - 冒頭コメントを更新(役割と元との差分を追記)

変えていない点:
  - I2C 受信ロジック(receiveEvent / CMD_SYNC の扱い)
  - 出力 CSV のスキーマ(addr,bar,interval_us,drift_us)
  - Serial ボーレート(115200)
  - MY_I2C_ADDRESS の切り替え運用(1ファイルで使い回し)

使い方:
  1. MY_I2C_ADDRESS を測りたいボードに書き換える(0x10〜0x13)
     ppm 値は #if で自動選択されるので他は触らなくてよい
  2. master を別ボードで走らせる(無補正のまま)
  3. シリアル(115200)を CSV にリダイレクトして 5回ぶん取る
       例(mac): cat /dev/cu.usbmodemXXXX > flute_drift_corrected.csv

期待される結果:
  ppm 補正が正しく効いていれば drift_us はほぼ 0 に収束する。
  残差は ISR 内 micros() のノイズ床、概ね std ≒ 120µs。

残差が大きかったら:
  該当アドレスの #elif 節の ppm 値と、対応する *_slave.ino の
  CLOCK_DRIFT_PPM を同じ値に書き換えるだけで再フィット可能。


3. 並行して詰めた内容(補正の仕組みに関する質問)
------------------------------------------------

(a) ppm 補正は何をしているか
    実行中に何かを測ったり学習したりはしない。事前に決めた ppm 定数を
    使って、calcBarUs() の戻り値を「公称小節長 × (1 + ppm/100万)」に
    伸縮させているだけ。

(b) なぜ「micros() で測る必要」と書いていたか(私の表現ミス)
    補正のために何かを測っているわけではない。スレーブはもともと
    micros() ベースで音符を発火する構造(barStartUs = micros()、
    fireUs = barStartUs + 拍番号 × beatUs)。ppm 補正は beatUs の値を
    1か所伸び縮みさせているだけで、新しい測定はしていない。

(c) なぜ小節長を変えるだけでズレが直るか
    時計の比喩で言うと、flute は秒針が +1419ppm 速い時計。flute の
    micros() で 500,000 進んだ瞬間は実時間で 499,290µs しか経っていない
    (708µs 早い)。だから fireUs を 500,710 にしておけば、micros() が
    500,710 に達するのが実時間で 500,000µs 後になり、master の意図する
    拍にぴったり揃う。

(d) SYNC 受信タイミング自体には触っていない
    SYNC 受信時は barStartUs = micros() で毎回リセットされるので、
    小節間で累積する誤差はゼロ。補正対象は「SYNC と SYNC の間の
    補間期間(2秒間)」の刻みだけ。

(e) CSV のズレは I2C 順次配信由来ではなく micros() ドリフト由来
    drift_measure は「連続2回の SYNC 受信間隔」を見るので、I2C の
    順次配信遅延は毎回ほぼ一定 → 引き算で相殺されて消える。残るのは
    各スレーブの micros() の刻みと実時間のズレ(=クロックドリフト)。

(f) 楽器ごとに ppm が違う理由
    micros() のズレはソフトの問題ではなくハードの個体差。クロック源
    (UNO R4 WiFi の場合は Renesas RA4M1 の内蔵 HOCO と推定)の発振
    周波数が個体ごとに製造ばらつきで違う。HOCO は精度 ±1% クラスなので
    数千 ppm レベルでバラつくのは仕様内挙動。organ だけ符号逆なのも
    分布の中心からマイナス側に出ただけ。

(g) ボード個体と楽器の対応は固定が必要
    ppm 値はボード個体に紐づくので、ボードを物理的に入れ替えたら
    補正がデタラメに当たる。物理ラベル(マスキングテープに楽器名と
    I2C アドレスと ppm 値を書いて貼る)で対応関係を固定する運用が安全。

(h) ケーブルは ppm 値に直接効かない
    クロック源は基板上の部品で完結。USB / 電源ケーブルは「電源条件」を
    通して間接的に効きうるので、計測時と本番で給電方法は揃える。
    I2C 配線(SDA/SCL)は通信遅延に影響するが drift_measure では相殺されて
    出てこないので ppm 値には影響しない。

(i) PLL 補正との違い
    目的は同じ(自分の micros() を実時間に合わせる)。違いは合わせ方:
      ppm = 事前に外で測った値を焼き込み (オープンループ)
      PLL = 実行中に自動学習         (クローズドループ)
    両者は対立せず、PLL は ppm の上に乗せられる。判断は「6:23 bpm-誤差対策2
    /補正方式比較.txt」参照。現状は ppm のみ で様子見の方針。


4. 次のアクション
-----------------
1. drift_measure_2.ino を各ボードに焼いて、5回ずつ CSV を取る
2. 残差の平均と std を集計
3. 平均が ±数百µs に収まれば ppm 補正のみで運用継続
4. 平均が大きい/長時間運用で後半ズレるようなら PLL 追加を検討
